# Build a Private Personal Cloud Storage Web App

I want you to build a complete, production-ready private cloud storage web application using **Replit Agent**, **Supabase**, and my existing domain.

The application should feel similar to a very simple private version of Google Drive, but the main purpose is secure personal/private file storage.

## 1. Core concept

When someone opens my domain, they should NOT immediately see the storage dashboard.

The flow should be:

1. Open my domain.
2. Show a clean private login/access page.
3. User authenticates using Supabase Auth.
4. Authentication should initially support:

   * Google Sign-In
   * Email/password or magic-link authentication if appropriate
5. After authentication, check whether the user has already created a private access passcode.
6. If the user has never created a passcode:

   * Show "Create your private passcode".
   * Let the user create a passcode.
   * Confirm the passcode.
   * Store ONLY a secure hash of the passcode.
7. If the user already has a passcode:

   * Ask them to enter the passcode.
   * Only after the correct passcode is entered should they access the storage dashboard.
8. The passcode belongs to the authenticated user.
9. Different authenticated users must have completely separate storage and accounts.
10. Users must never be able to see another user's files.

The passcode is an additional application-level security layer. **Do NOT use the passcode as the Supabase Auth password.**

# 3. Private passcode system

Every user should have their own private passcode.

Example:

User A:

```text
Google account → user A
Private passcode → 824619
Files → User A's files only
```

User B:

```text
Google account → user B
Private passcode → 391572
Files → User B's files only
```

The same application/domain can support multiple users, but each user must have completely isolated data.

### Passcode requirements

Allow the user to create a passcode.

Prefer a 6-digit numeric passcode initially.

Add:

* Passcode
* Confirm passcode
* Show/hide passcode
* Basic validation
* Prevent empty passcodes
* Prevent obviously invalid values such as `000000`
* Rate-limit incorrect attempts
* Temporary lockout after too many failed attempts

Do NOT store the raw passcode in the database.

Use a secure password hashing mechanism such as Argon2id or another appropriate server-side password hashing method.

The database should contain something similar to:

```text
passcode_hash
```

and never:

```text
passcode
```

       ↓

Do not allow someone who only knows another user's email address to reset their passcode.

Use Supabase Auth's secure recovery mechanisms.

After a successful reset, invalidate any old passcode session/access state.

# 7. Supabase Storage architecture

Use **Supabase Storage** for the actual files.

Do NOT store uploaded files directly inside PostgreSQL.

Use a private Supabase Storage bucket, for example:

```text
user-files
```

Each user's files must be stored inside a user-specific path.

For example:

```text
user-files/
    USER_ID_1/
        documents/
        images/
        videos/

    USER_ID_2/
        documents/
        images/
        videos/
```

Use the authenticated Supabase user ID to isolate storage.

Example:

```text
user-files/{user_id}/filename.ext
```

Implement proper Supabase Storage Row Level Security/storage policies so that:

```text
User A → can access only User A files
User B → can access only User B files
```

Never rely only on frontend filtering for security.

# 14. Security requirements

This is extremely important.

Implement:

### Authentication security

* Supabase Auth
* Protected routes
* Secure session handling
* Logout
* Session expiration handling

### Passcode security

* Never store raw passcodes
* Hash passcodes securely
* Rate-limit attempts
* Temporary lockout after repeated failures
* Do not expose passcode hashes to the frontend
* Do not place passcodes in localStorage
* Do not put passcodes in URLs
* Do not log passcodes

### Database security

Enable Supabase Row Level Security.

Every user-specific table must have policies based on:

```sql
auth.uid()
```

### Storage security

Supabase Storage policies must ensure users can only access their own storage paths.

Never rely on frontend checks alone.
